## Summary

**107 findings: 0 critical, 6 major, 76 minor, 25 nit.** The post-106-fix code is in strong shape — the pure-state-machine seams are single-sourced, the shared `GeometricSelectionEngine` extraction (M4) landed and both surfaces delegate to it, logging is centralized, net472 compliance is clean, and both offline suites pass (319 + 236). The sharp edges are: (1) **the query-driven finder UI-thread residuals** — the fzf literal-fallback scan, the sync `GetCandidates`, and the CodeIssues TODO scan still block the UI thread (the exact freeze class M1/M2/M3 were meant to eliminate); (2) **a real fzf correctness bug** — on timeout/crash/whitespace query, `FzfFilter` returns the FULL candidate list and the finder maps it all back as matches (Enter opens a random file at a random line); (3) **the M6 navigation isolation is incomplete** — `LinkedTo`/`FindActive` still read stale RCWs with no per-window try/catch, so one stale frame can still kill all navigation; (4) **the stale-toolwindow sentinel is never armed in production** — `neovisual-explorer-move-editor-focus` is a false-green; (5) a **timing-dependent flaky test** (`Run_FzfFilter_GraceDelayToken`); and (6) an **architecture-contract doc drift** (spec.md §2.5 + SKILL.md misattribute the geometric pipeline to `WindowNavigationEngine` instead of the shared `GeometricSelectionEngine`).

## Detailed findings

### M1 (major) — the stale-toolwindow sentinel is never armed in production → false-green e2e

- **Where:** `MyExtension/Input/InputHandler.cs:524-531` (the `_sentinelArmed` gate) + `:203` (`SetSentinelArmedForTest`).
- **What's wrong:** `_sentinelArmed` is only ever set by the internal test seam `SetSentinelArmedForTest` (called from `tests/NeoVisual.Tests/Program.cs:3252`). In a live/e2e run it stays `false`, so `RefreshStaleSentinel()` is never called and the `stale-toolwindow` file the harness creates (test-e2e.ps1:1403) is never stat'd — `StaleToolWindowSentinel.IsStale` stays false forever.
- **Why it bites:** `neovisual-explorer-move-editor-focus` becomes a false-green: the stale-frame + editor-focused combination the FocusGuard leak guard exists for is never exercised live. The scenario passes only because the natural non-tool-window state also prevents the leak — so a future FocusGuard regression in the stale-frame path goes undetected. The m11 fix (guarding the `DateTime.UtcNow` read behind `_sentinelArmed`) correctly removed the per-key clock cost, but it also disarmed the production path.
- **Fix:** Arm the sentinel when the harness is present (e.g. `_sentinelArmed = StaleToolWindowSentinel.Path != null` at construction, or refresh the sentinel from a production-reachable path gated on the harness env var), so the e2e fault injection actually exercises the guard.

### M2 (major) — M6 isolation is incomplete: `LinkedTo`/`FindActive` still read stale RCWs with no per-window try/catch

- **Where:** `MyExtension/Navigation/Utils/WindowFrameAdapter.cs:105` (`FindActive`'s `FirstOrDefault(a => CompareWindows(activeWindow, a.DteWindow))`) and `:121` (`LinkedTo`'s `Where(a => parentWindows.Any(p => CompareWindows(p, a.DteWindow)))`).
- **What's wrong:** The M6 fix wrapped `GetLinkedWindowsList` (WindowFrameUtils.cs:57-76) in a per-window try/catch, but the two call sites that then re-read `a.DteWindow.Caption`/`Type` for EVERY adapter in the full enumerated list are not isolated. A stale/disconnected RCW anywhere in the tool+document frame list throws COMException out of `CompareWindows`, propagating through `BuildActiveWindows` into the `WindowNavigator` ctor catch, which zeroes `_activeWindows`/`_activeWindow`. Because the static cache is only populated on success, every subsequent keystroke with the same (unchanged) adapters list re-throws and re-no-ops — navigation is stuck until a focus change re-enumerates.
- **Why it bites:** This is exactly the "one stale frame must not kill all navigation" failure F7/M6 claimed to fix, but the isolation only covers `GetLinkedWindowsList`, not the `Where` clause or `FindActive`. A single window closed between focus changes silently disables window navigation for the whole window-set.
- **Fix:** Wrap the `CompareWindows(p, a.DteWindow)` call in `LinkedTo`'s `Where` clause and `FindActive`'s `FirstOrDefault` predicate in the same per-window try/catch (skip the throwing adapter) that `GetLinkedWindowsList` uses.

### M3 (major) — fzf timeout/crash/whitespace returns the FULL candidate list → garbage results

- **Where:** `Telescope/Filter/FzfFilter.cs:308` (timeout path `return lines;`), `:329` (crash path `return lines;`), `:175` (whitespace query) + `Telescope/Finders/FzfFinder.cs:136` (`await _fzf.FilterAsync(...)` then `MapBatched` maps it all back).
- **What's wrong:** `FilterAsync`'s graceful-degradation contract (return the unfiltered list) is correct for the FileFinder path but catastrophic for the FzfFinder path: on a timeout, a crash, or a whitespace-only query (which passes `FzfFinder`'s `IsNullOrEmpty` check at :90 but trips `FzfFilter`'s `IsNullOrWhiteSpace` at :175), the finder maps the ENTIRE candidate list back via `MapBatched` and shows the first `HitCap=200` lines of the solution as if they matched. Enter opens a random file at a random line.
- **Why it bites:** The user types a query, fzf hangs (>3s) or dies, and the finder shows garbage matches; a space query triggers it deterministically. The `FzfFinder` cannot distinguish "fzf genuinely matched everything" from "fzf failed and returned everything".
- **Fix:** Have `FzfFilter` signal failure distinctly (return `null` / throw a typed exception) instead of returning the unfiltered list, and have `FzfFinder` treat that as empty-or-literal-fallback; also make `FzfFinder`'s empty-query check `IsNullOrWhiteSpace`.

### M4 (major) — the query-driven finder UI-thread residuals (the M1/M2/M3 freeze class, partially back)

- **Where:** `Telescope/Finders/FzfFinder.cs:135-155` (the post-`await Task.Run` continuation runs `BuildCandidates` + `FilterAsync` + `MapBatched` + the literal-fallback `Scan` loop on the UI SynchronizationContext — no `ConfigureAwait(false)`), `GrepFinder.cs:63-69` (the sync `GetCandidates` override calls `GetCandidatesAsync(query).GetAwaiter().GetResult()` — a UI-thread block for a non-empty query), `CodeIssuesFinder.cs:95-101` (`Task.Run(...).GetAwaiter().GetResult()` blocks the UI thread for the whole TODO scan).
- **What's wrong:** The M1/M2/M3 fixes moved the file I/O off the UI thread but left the CPU-bound mapping/scan work on it. The fzf literal-fallback path (fzf unavailable) scans every file's lines on the UI thread per keystroke; the sync `GetCandidates` is a UI-thread deadlock trap if ever invoked with a non-empty query; the CodeIssues open still blocks for the whole solution TODO scan.
- **Why it bites:** On a real (large) solution, the Fzf finder with fzf unavailable freezes the overlay per settled keystroke (~1M line scans for 100 files × 10k lines), and the Issues finder open freezes for the whole scan. The e2e scratch solution is too small to catch it, so this ships green.
- **Fix:** Move the whole gather (read + `BuildCandidates` + `FilterAsync` + `MapBatched`, and the literal scan) inside the `Task.Run`, returning the mapped hits; make `GrepFinder`'s sync `GetCandidates` throw for a non-empty query (mirror `FzfFinder.cs:82`); make `CodeIssuesFinder.GatherHits` async (or `JoinableTaskFactory.Run`) so the open doesn't block.

### M5 (major) — `Run_FzfFilter_GraceDelayToken` is a timing-dependent flaky test

- **Where:** `tests/Telescope.Tests/Program.cs:5683`.
- **What's wrong:** `Thread.Sleep(150)` assumes the 100ms timeout has fired, and `sw.ElapsedMilliseconds <= 150` is a wall-clock bound on the post-cancel return. On a slow/loaded machine the timeout may not have fired by 150ms (cancel before timeout → fast return → false GREEN without the m9 token fix), or the post-cancel return may exceed 150ms (spurious failure).
- **Why it bites:** A flaky test that sits deliberately at a timing boundary — it will fail intermittently on slow CI machines, and worse, it can pass without the fix it claims to pin.
- **Fix:** Drive timeout+grace through the existing `DelayFactory` seam (controllable tasks) and assert the grace delay's token is observed, not elapsed time.

### M6 (major) — the docs misattribute the geometric pipeline (architecture-contract drift)

- **Where:** `docs/spec.md:202-204` + `.opencode/skills/vs-extension-dev/SKILL.md:148-149`.
- **What's wrong:** Both claim "the collapsed FocusTargetModel runs the WindowNavigationEngine pipeline ... over the pane rects". The 106-fix M4 extraction moved both pane-focus and window-nav onto the shared `GeometricSelectionEngine` — `FocusTargetModel.cs:289` calls `GeometricSelectionEngine.SelectTarget(...)` and `WindowNavigationEngine.cs:15` ALSO delegates to it. The doc omits the shared engine and misattributes the pipeline to `WindowNavigationEngine`, a cross-project dependency that does not exist.
- **Why it bites:** spec.md is the architecture contract ("must never drift from reality"). A reader (or a future planner) believes the pane focus runs the window-nav algorithm and plans changes against the wrong seam; the two surfaces are actually already unified.
- **Fix:** "FocusTargetModel runs the shared GeometricSelectionEngine (the same engine WindowNavigationEngine delegates to)".
