## Detailed findings

### R1 (major) — the M1 fix broke prompt selection navigation (j/k/g/G) and a/A/I placement

- **Where:** `Telescope/Overlay/TelescopeOverlay.cs:571` (the `TryPromptMotion` gate), `:592-611` (`TryPromptMotion`); `Telescope/Overlay/Utils/PromptMotionRouter.cs:34-35` (default branch returns true for any non-insert motion); `Telescope/Overlay/Utils/TextMotionDispatcher.cs:78-88` (`MapKey(Key, bool)` maps `J`→Down, `K`→Up, `G`→Top/Bottom); `Telescope/Overlay/Utils/OverlayKeyHandler.cs:142-167` (`OverlayKey.J/K/G/ShiftG` → `MoveDown`/`MoveUp`/`MoveToFirst`/`MoveToLast`).
- **What's wrong:** The M1 fix routed prompt motions through the shared `TextMotionDispatcher` so `a`/`A`/`I` would fall through to insert mode. But `TextMotionDispatcher.MapKey` maps `j`/`k`/`g`/`G` to Down/Up/Top/Bottom (motions for the *preview* surface), and `PromptMotionRouter.ShouldConsume` returns `true` for ANY non-insert motion. So in normal mode with the prompt focused, `TryPromptMotion` consumes `j`/`k`/`g`/`G` as caret motions (`e.Handled = true`, returns before `_keyHandler.Handle`), and `OverlayKeyHandler`'s selection navigation is unreachable. Additionally, `TryPromptMotion` discards the `insertPlacement` out param (`out _`, line 595), so `a` (InsertAfter) and `I` (InsertStart) fall through to `MapKey(e.Key)` → `OverlayKey.A`/`OverlayKey.I` → `EnterInsertMode(CaretPlacement.End/Current)` — `a` appends at END (not after the caret) and `I` inserts at CURRENT (not line start). `OverlayAction.EnterInsertStart` is dead code.
- **Why it bites:** This is the **core Telescope navigation**: `j`/`k` no longer move the selection and `g`/`G` no longer jump to first/last in the prompt — the exact behavior `telescope-navigate` (asserts `selected=1/2/1/0` and G→last, gg→first) and `telescope-wrap` (asserts wrap-around) pin. Those scenarios are QUEUED-not-run (no VS boot on this machine), so the regression is uncaught; the unit tests cover only a/A/I (the M1 test) and the pure `OverlayKeyHandler`, never `TryPromptMotion`. A user on a VS-capable machine will hit broken list navigation the moment the deferred e2e suite runs.
- **Fix:** Restrict the prompt motion set in `PromptMotionRouter.ShouldConsume` to h/l/w/b/e/0/$ (return false for Down/Up/Top/Bottom), and capture the `insertPlacement` out param so `a`/`A`/`I` route to the correct `CaretPlacement` (after-caret / end / start). Add a unit test asserting `TryPromptMotion` does not consume `j`/`k`/`g`/`G` and that `a`/`I` produce the vim-correct placements.

### R2 (major) — preview rebuilds the whole FlowDocument per selection change (M4 partial)

- **Where:** `Telescope/Overlay/Utils/PreviewRenderer.cs:66-131` (`SetContent` unconditionally rebuilds `FlowDocument` + `_lineIndex` + `_linePointers` + `ScrollToHome()`), `:51` (`Show` calls it on every selection change); caller `TelescopeOverlay.cs:450→471` (`LoadPreviewForSelection` per j/k move and filter update).
- **What's wrong:** The M4 fix added `PreviewTokenCache` (line 38) so tokenization is cached, but the WPF document rebuild is not gated. The docstring (lines 21-22) claims "re-read and re-tokenized only when LastWriteTimeUtc changes" — only the tokenize half is true.
- **Why it bites:** Moving the selection between hits in the same large file re-creates ~1 Run/paragraph per line and resets the preview scroll per keystroke — the dominant remaining preview cost and the exact "scroll/caret destroyed by moving list selection" failure M4 flagged.
- **Fix:** Cache the built `FlowDocument` + `_linePointers` keyed by mtime (mirror `PreviewTokenCache`); only rebuild when content changes; keep `MoveToLine`/`ApplyCaret` as the per-selection work.

### R3 (major) — VimModeSource buffer-subscription lifecycle leak

- **Where:** `MyExtension/Vim/Utils/VimModeSource.cs:263-281` (`UnsubscribeBuffer` removes the `SwitchedMode` subscription but never the `Closed` subscription added at `:254-255`), `:247,270` (`_subscribedBuffers` only cleared in `OnBufferClosed`), `:183-197` (`OnBufferClosed` never decrements `_textBufferRefCounts`).
- **What's wrong:** Three inconsistent lifecycle paths: (1) a view closed while its document buffer stays open (split view, preview tab) leaves the buffer referenced by `_subscribedBuffers` AND the buffer referencing `this` via the `Closed` event — a persistent leak; (2) a later re-attach of the same buffer hits `_subscribedBuffers.Add == false` and never re-subscribes `Closed`, so the buffer's close is never cleaned up; (3) `OnBufferClosed` doesn't decrement the refcount, so the last view's `Detach` decrements to 1 (never 0) and `UnsubscribeBuffer` is never called.
- **Why it bites:** This is the VsVim interop surface (the highest-blast-radius fragile surface per prior reports). A stale `_currentTextBuffer` can mis-route a later `SwitchedMode` event into the wrong view's mode state — the exact silent mode-detection degradation class F5/m39/m40 were built to prevent. The leak also grows per closed-but-open document.
- **Fix:** Add a `remove_Closed` invocation + `_subscribedBuffers.Remove(buffer)` in `UnsubscribeBuffer` (mirroring the `SwitchedMode` removal), and decrement `_textBufferRefCounts` in `OnBufferClosed` (removing the entry at 0).

### R4 (major) — frame enumeration has no per-frame fault isolation

- **Where:** `MyExtension/Navigation/Utils/WindowFrameAdapter.cs:67,71` (`Enumerate` uses `ErrorHandler.ThrowOnFailure` on `GetToolWindowEnum`/`GetDocumentWindowEnum`), `:140-154` (`ExtractFramesCore` — an unguarded `VsShellUtilities.GetWindowObject(frame[0])` per frame); caller `WindowManager.GetWindowAdapters` (WindowManager.cs:206) has no try/catch and runs BEFORE the `WindowNavigator` ctor's defensive catch (InputHandler.cs:498).
- **What's wrong:** A single frame whose `GetWindowObject` throws (torn-down frame) or whose `frames.Next` returns an error HRESULT aborts the whole `Enumerate` via `ThrowOnFailure`, killing ALL navigation. The m46 per-window isolation only covers the rect snapshot in `NavigateInDirection`, not the frame enumeration.
- **Why it bites:** The exception escapes `Navigate` into the keyboard-hook path — the exact "never throw into the keyboard hook" invariant the rest of the slice defends (m44/m46) — and, if caught by the M15 binding guard, is misdiagnosed as a binding failure instead of a navigation failure.
- **Fix:** Wrap each frame's `GetWindowObject` in try/catch and skip the bad frame (log once), and wrap the two `ThrowOnFailure` calls (or the whole `Enumerate` body) to return an empty list on failure, mirroring the existing null-`uiShell` path.

### R5 (major) — `telescope-mode` `i`/`a` insert-mode assertions are false positives

- **Where:** `tools/harness/test-e2e.ps1:578-588`.
- **What's wrong:** `Reset-LogBaseline` (line 578) runs BEFORE `Open-Telescope` (line 579). `Open-Telescope` emits `Focus prompt => True, mode=insert` (per AGENTS.md it waits for that line before returning). So the Open-Telescope line is inside the fixed search window and satisfies all three `Assert-NewLogLine 'Focus prompt => True, mode=insert'` calls (lines 580, 585, 588) — including the `i` and `a` taps — even if `i`/`a` never enter insert mode.
- **Why it bites:** The scenario cannot fail on the exact regression it guards. The M1 `a`/`A`/`I` prompt-interception bug was fixed production-side, but the harness gate was never hardened — a re-introduction of the bug (or the R1 placement regression) would pass the e2e suite silently.
- **Fix:** Snapshot the log index just before the `i`/`a` tap and use a post-tap search for a NEW `Focus prompt => True, mode=insert`, or assert the `key=I mode=normal handled=True` / `key=A mode=normal handled=True` line for the tap (the `key=... mode=... handled=...` diagnostic already exists).
